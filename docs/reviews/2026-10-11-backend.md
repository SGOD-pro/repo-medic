## Minor

### ?? `finish_run` best-effort catch is too broad, `backend/src/storage/repository.py:158`

**Problem**: The try/except wraps only `append_event` (correct, matches the stated intent). However, the catch is `except Exception` which will also silently eat `AttributeError`, `NameError`, or any programming bug inside `append_event` itself, not just network errors. In a production-quality codebase this degrades into "the run.finished event just never appeared and nobody knows why".

**Why it matters**: Transient infrastructure errors (bridge down, 5xx) are correct to swallow. Programming bugs (AttributeError etc.) should propagate because they indicate a code defect, not a transient failure.

**Suggested fix**: Narrow to `except (httpx.RequestError, httpx.HTTPStatusError, OSError)` and let unexpected exception types propagate.

---

### ?? `run_standalone` with `max_runs=0` exits immediately with no documented contract, `backend/src/worker.py:187`

**Problem**: `while max_runs is None or runs_processed < max_runs` evaluates `0 < 0` as False when `max_runs=0` and exits without processing anything. This is internally consistent but surprising — a caller could reasonably assume `max_runs=0` means "dry-run" or "process all but count zero". No test exercises this edge case.

**Why it matters**: This is a latent contract/documentation issue. Not a production bug today since `run_standalone` with `max_runs=0` is not called anywhere in the app, but could catch a future caller off-guard.

**Suggested fix**: Document the edge case in the `run_standalone` docstring, e.g. "Pass `max_runs=0` to exit immediately without processing any runs."

---

### ?? Non-CAS PATCH error message is misleading for the non-race case, `db-worker/src/index.ts:382`

**Problem**: The error message `"Run transitioned to a terminal state during this update"` implies the transition happened concurrently **during** this request. But if the run was already terminal before the request arrived (e.g., a second `finish_run` call after the first succeeded), the message is factually incorrect.

**Why it matters**: Operational debuggability — misleading error messages make log-driven incident triage slower.

**Suggested fix**: `"Run is in a terminal state and cannot be updated"` — accurate for both the race and non-race scenario.
