## Summary
This change completes checkpoint K2 by connecting the offline engine repair pipeline to QueueWorker and switching the frontend to real HTTP transport and Server Sent Events. The end to end flow successfully exercises sequential repair, branch and refine search, run cancellation, and crash restart recovery. However, several significant issues must be resolved before merge: two static type check failures in backend repository mapping, a React effect loop causing UI flashing on task card selection, a false connection loss banner rendered on clean stream completion, and potential run stranding in the worker on recipe load errors.

## Major

### 🟠 Task selection triggers redundant network refetch and UI flash, `frontend/src/components/tasks-view.tsx:118`
**Problem**: The fetchTasks callback includes selectedTaskId in its dependency array. Whenever a user clicks any task card to select it, selectedTaskId changes, which re-creates fetchTasks and triggers the useEffect hook. This immediately sets loading to true, unmounts the rendered task list, shows a loading spinner, and issues a redundant HTTP request for the task list.
**Why it matters**: Selecting a task card is a primary user interaction. Wiping the UI and showing a spinner on every click creates noticeable UI jank. If the network is slow or transiently drops, clicking an already loaded card can show an error or delay selection.
**Suggested fix**: Remove selectedTaskId from the fetchTasks dependency array. If default selection of the first task is needed when no task is selected, set the initial selection once upon receiving the task list using an internal ref or functional state updater rather than watching selectedTaskId in the fetch hook.

### 🟠 Clean stream completion displays connection lost failure banner, `frontend/src/components/run-active-view.tsx:589`
**Problem**: When an execution completes normally, StreamManager receives the run finished event and calls its stop method, setting connectionStatus to disconnected. In RunActiveView, line 589 checks only connectionStatus equals disconnected and not cancelled, without verifying whether the run has reached a terminal or successful state. As a result, the UI displays the event stream connection lost banner stating that reconnection failed after five attempts, along with a red disconnected badge.
**Why it matters**: Every successful or cleanly finished repair run alarms the user with an apparent network failure banner claiming that five reconnection attempts failed, despite the run succeeding cleanly.
**Suggested fix**: Check that the run is not in a terminal state before displaying the disconnection banner, or gate the banner on errorDetail with code CONNECTION_CEILING_REACHED or an exceeded retry count rather than generic disconnected status.

### 🟠 Transport mode conflated with run execution mode, `frontend/src/components/run-active-view.tsx:64`
**Problem**: The isHttpMode flag is calculated as process.env.NEXT_PUBLIC_API_TRANSPORT equals http or activeRun.mode equals offline or activeRun.mode equals live. In MockTransport, runs are created with mode set to live or offline. Because of this, isHttpMode evaluates to true even when running with the mock transport.
**Why it matters**: When developers or demo users run the frontend in mock mode, the mock candidate cards and mock pipeline stages are bypassed completely. The synthetic mock execution view is rendered unreachable, and the active view attempts to listen to real event streams while displaying live sandbox badges.
**Suggested fix**: Determine transport mode exclusively from NEXT_PUBLIC_API_TRANSPORT or the client transport type rather than checking activeRun.mode.

### 🟠 Static type check failure on RunSummary mode and search_mode, `backend/src/storage/repository.py:90`
**Problem**: In D1StorageRepository._map_run_summary, raw_mode and raw_search are extracted as strings, but the variables mode and search_mode are inferred as str. Passing them to RunSummary fails mypy static type checking with two errors because RunSummary requires literal types Mode and SearchMode.
**Why it matters**: Running mypy on the backend source tree now fails, breaking the static analysis gate and type safety guarantees between storage records and Pydantic contracts.
**Suggested fix**: Narrow or cast mode and search_mode to the literal types Mode and SearchMode before constructing RunSummary, using typing.cast or explicit type annotations.

### 🟠 Task recipe loading outside exception block strands running runs, `backend/src/worker.py:159`
**Problem**: In QueueWorker.process_one, the run is transitioned from queued to running in the database at line 135. However, load_task_recipe at line 159 is executed outside the try block that catches unhandled exceptions. If loading or parsing the recipe raises an error, the exception escapes process_one into the outer run loop.
**Why it matters**: The run is left stranded in running state in the database with no terminal state update and no run.finished event, violating acceptance criterion AC-6 and the reliable final event invariant of specification 0003. Future worker polls ignore the stranded run because they only query for queued runs.
**Suggested fix**: Move the try block earlier to wrap request construction, task recipe loading, and HostPorts initialization, ensuring any exception triggers finish_run with failed state.

## Minor

### 🟡 Fixture title and target version inconsistency, `fixtures/tasks/TASK-084.json:3`
**Problem**: The fixture title in TASK-084.json says pydantic v1.10.8 to v2.0.2 migration, but line 8 sets to_version to 2.0.0. In frontend api.ts, both title and to_version were changed to 2.0.0, leaving the fixture file inconsistent with frontend definitions.
**Why it matters**: Conflicting version numbers in test fixtures cause confusion across teams and can result in mismatched assertions during validation.
**Suggested fix**: Update the title in TASK-084.json to specify 2.0.0 to match to_version and the frontend task summary.

### 🟡 Hardcoded developer specific filesystem paths in browser tests, `frontend/tests/browser_acceptance.mjs:6`
**Problem**: The browser acceptance test script contains hardcoded paths to a specific developer home directory (/home/swyra/.gemini/antigravity-cli/brain/...) and project repository path (/home/swyra/projects/repo-medic/backend). Similarly, verify_playwright.mjs contains a Windows user path (C:\Users\KIIT\...).
**Why it matters**: These scripts will immediately fail with file not found errors when executed in continuous integration environments or on other developer machines.
**Suggested fix**: Use relative paths derived from process.cwd() or import.meta.url, and accept optional artifact directory overrides via environment variables.

### 🟡 Browser acceptance script not registered in package scripts, `frontend/tests/browser_acceptance.mjs`
**Problem**: The new acceptance test file browser_acceptance.mjs is placed in frontend/tests but uses the .mjs extension, so the test script in package.json (which runs tests/*.test.ts) does not execute it.
**Why it matters**: Acceptance tests that are not wired into standard npm test or CI scripts easily become stale and rot over time.
**Suggested fix**: Add an explicit script command in package.json such as test:acceptance and document how to start the prerequisite local services before running it.
