## Summary
The changes implement the remote Cloudflare D1 integration foundations for checkpoint K3, adding fail closed worker authentication, scoped queue worker and recovery polling, exact manifest cleanup, preflight verification checks, and acceptance test coverage. The core authentication logic and exact manifest cleanup mechanisms are well designed, and the test suite passes cleanly in offline simulation. However, three major issues prevent clean deployment and repeatable testing: tests insert uncleaned static records that cause HTTP 409 conflict failures on second test execution against remote D1, the preflight verification command fails when executed from the backend directory because it cannot find the local wrangler installation, and the preflight module contains a hardcoded absolute path to a specific local user directory.

## Major
### 🟠 Persistent test records with static IDs break repeated runs against remote D1, `backend/tests/test_k3_remote_d1.py:328`
**Problem**: The tests `test_persistence_across_restart` and `test_exact_manifest_cleanup_preserves_unrelated_records` create records with hardcoded static identifiers (`run_unrelated_persist_keep` and `run_permanent_unrelated`) that are deliberately excluded from `k3_manifest` and never deleted after the test finishes.
**Why it matters**: In offline simulation with fresh SQLite transports, this issue remains hidden. When executed against a shared or persistent remote D1 database, running the test suite a second time immediately crashes with HTTP 409 Conflict when attempting to reinsert the same run identifier, and leaves permanent records in running state in the database.
**Suggested fix**: Delete the non manifest test records explicitly during test teardown after asserting that `cleanup_manifest` preserved them, and use dynamic run identifiers with timestamps or unique prefixes.

### 🟠 Preflight check CLI fails to resolve wrangler when executed from backend directory, `backend/scripts/preflight_check.py:72`
**Problem**: In `backend/scripts/preflight_check.py`, `run_command` invokes `npx wrangler` without setting the subprocess working directory to the directory containing `wrangler.toml` and `package.json` (`db-worker/`).
**Why it matters**: Following the instructions in `verify.md` (`cd backend && uv run python scripts/preflight_check.py --remote`) causes `npx` to fail finding the project local wrangler binary in `db-worker/node_modules/.bin/wrangler`. Instead, `npx` pauses asking interactively to download wrangler or fails in non interactive environments, and cannot locate `wrangler.toml`.
**Suggested fix**: Set the subprocess working directory in `run_command` to the parent directory of `args.wrangler_path`, or invoke wrangler by passing `--config` with the absolute configuration path.

### 🟠 Hardcoded user specific path in preflight module, `backend/src/preflight.py:124`
**Problem**: The default parameter in `run_preflight` hardcodes `/home/swyra/projects/repo-medic/db-worker/wrangler.toml`.
**Why it matters**: Calling `run_preflight()` without an explicit path fails on any other machine, container, or CI environment because the path depends on a specific local user home directory.
**Suggested fix**: Resolve the path dynamically relative to the current file location using `Path(__file__).resolve().parents[2] / "db-worker" / "wrangler.toml"`.

## Minor
### 🟡 Acceptance manifest dump on failure is never invoked, `backend/tests/test_k3_remote_d1.py:58`
**Problem**: The method `dump_on_failure` is implemented on `AcceptanceManifest` but is never called anywhere in the test suite.
**Why it matters**: Spec 0005 states that when an acceptance test assertion fails, cleanup is skipped and the manifest is written to `artifacts/k3_manifest_<timestamp>.json` for operator diagnosis, but currently the file is never produced.
**Suggested fix**: Invoke `dump_on_failure` in a pytest fixture teardown or exception handler when a test failure occurs before returning.

### 🟡 Vacuous assertion in offline simulation test, `backend/tests/test_k3_remote_d1.py:96`
**Problem**: `test_simulation_notice_does_not_claim_remote_acceptance` only asserts that the character length of a hardcoded string literal is greater than zero.
**Why it matters**: The test passes unconditionally without exercising any code paths or checking system configuration, creating misleading coverage metrics.
**Suggested fix**: Assert meaningful properties such as verifying that the transport is an offline simulation instance, or remove the vacuous assertion.

### 🟡 Missing coverage for global budget cap and invalid event sequences, `backend/tests/test_k3_remote_d1.py:268`
**Problem**: Acceptance criteria AC-5 requires verifying that invalid event sequences leave zero partial rows, and AC-6 requires verifying that the global 25 USD budget cap is atomically enforced. The test file docstring claims to test both, but `test_concurrent_budget_reservations` only tests per run limits and `test_zero_partial_writes_on_failure` omits event sequence checks.
**Why it matters**: Two explicit acceptance criteria from spec 0005 remain unverified in the remote acceptance test suite.
**Suggested fix**: Add a test case attempting sequential or concurrent reservations exceeding the global 25 USD cap to verify HTTP 409 rejections, and test that an invalid event sequence is rejected without partial writes.

### 🟡 SQL LIKE wildcard matching allows unexpected prefixes, `db-worker/src/index.ts:243`
**Problem**: Querying `run_id LIKE ?` with `${runPrefix}%` does not escape underscore characters in `runPrefix`.
**Why it matters**: Underscore is a single character wildcard in SQL LIKE queries. If an unrelated run matches the pattern with a different character (for example matching `run-k3-` instead of `run_k3_`), `worker.py` fetching `limit=1` will retrieve it, fail its `startswith` check, and return without processing, blocking other queued items.
**Suggested fix**: Escape underscore and percent characters in `runPrefix` using `ESCAPE '\'` in the SQL statement, or use exact prefix substring matching.

## Nits
- ⚪ `db-worker/src/index.ts:818`, `POST /api/cleanup` executes SQL `IN (...)` queries without chunking, which could exceed parameter limits if a manifest contains many items.

## Strengths
- Fail closed authentication logic in the worker correctly rejects unconfigured secrets with HTTP 500 auth_unconfigured and permits dummy tokens only under explicit local configuration.
- Exact manifest cleanup implementation enforces strict entity deletion ordering without broad pattern matching, preserving non target records.

However, live remote testing against a persistent database is blocked by static record conflicts on repeated runs, and test coverage is missing for the global 25 USD budget cap and invalid event sequence transactional guarantees.
