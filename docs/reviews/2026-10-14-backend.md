## Minor

### 🟡 `run_id` accepted from the caller in `POST /api/runs`, no server-side generation, `db-worker/src/index.ts:256`

**Problem**: The D1 bridge's `POST /api/runs` handler accepts `run_id` from the request body and inserts it directly. The Python backend generates the ID (`run_{uuid.uuid4().hex}`) and passes it through `db_client.create_run`, so in normal flow this is fine. But the bridge is the authoritative data store; nothing in it enforces that only the backend generates IDs. A caller who authenticates directly to the bridge (e.g. during testing, internal tooling, or a future engine integration) can supply an arbitrary string as `run_id`.

**Why it matters**: Specially crafted `run_id` values that contain path separators or injection characters could affect URL matching downstream (e.g. `run_id` of `"abc/operations"` or `"abc?state=queued"` could theoretically collide with other route patterns). The current routing uses explicit regex patterns (`/api/runs/([^/]+)/events$`) which `decodeURIComponent` is applied to, providing some protection — but the ID is never sanitised or format-validated at the bridge level. This is low severity today (the only auth path is through the Python backend), but it is a latent risk as integrations expand.

**Suggested fix**: Add a simple server-side `run_id` validation in the `POST /api/runs` handler: reject IDs that do not match a known safe pattern (e.g. `^[a-zA-Z0-9_-]{1,128}$`). This closes the latent injection surface without changing the API contract for compliant callers.
