## Minor

### 🟡 Swallowed create_execution failure silently downgrades to unclean sandbox, ackend/src/engine/verifier.py:124
**Problem**: When sandbox.create_execution(checkpoint_id) raises an exception, the code falls through to exec_sandbox = sandbox and sets checkpoint_isolated = False. Verification then continues inside the original (potentially contaminated) sandbox rather than aborting.
**Why it matters**: Isolation from the upgraded checkpoint is a security property of this feature. A live sandbox that raises on create_execution (connection timeout, quota, resource error) would silently run verification in a contaminated environment. The checks that follow still run and checkpoint_isolated is False, but nothing stops the run from producing a passed=True outcome with checkpoint_isolated=False.
**Suggested fix**: When checkpoint_isolated is False after the try block, short-circuit with a provisioning_failed reason rather than proceeding. The spec says "creates fresh execution... never reusing contaminated generation runtimes." Falling back to the original sandbox violates that invariant.

### 🟡 ailed_count in 	est_summary is incorrect for partial failures, ackend/src/engine/verifier.py:72
**Problem**: ailed_count is computed as 	est_res.collected_count if test_res.exit_code != 0 else 0. This assumes all collected tests failed if exit code is nonzero, which is wrong for suites where some pass and some fail (a common case in real repos).
**Why it matters**: EvidenceManifest.test_summary.failed_count is part of the auditable evidence record. Evaluators and Slice D consumers reading evidence.json would see an inflated failure count whenever any test fails.
**Suggested fix**: If CommandResult exposes ailed_count directly, use it. Otherwise, compute it as collected_count - passed_count - skipped_count. If there is no reliable source, omit ailed_count or label it unknown rather than over-reporting.

### 🟡 Hardcoded fallback hashes in ecord_baseline_preservation are the sha256 of empty string, ackend/src/engine/baseline.py:37
**Problem**: When hash_files() returns empty, the function falls back to a hardcoded dictionary where the first value (e3b0c44...) is the sha256 of an empty string. If the real test files are non-empty, these hashes will never match the real files, making the hash check always pass trivially (baseline and current hash both use the same placeholder).
**Why it matters**: In a live adapter path where hash_files is temporarily unavailable, the entire three-point hash invariant becomes a no-op. This would be a security regression on the feature primary purpose.
**Suggested fix**: Remove the hardcoded fallback, or replace it with a sentinel value that causes the hash check to be explicitly skipped rather than silently satisfied. The fake sandbox DEFAULT_TEST_HASHES already serves the deterministic testing need; the fallback in production code is the dangerous path.
