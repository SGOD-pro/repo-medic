## Minor

### ?? Propagated programming error from `finish_run` triggers a silent double-`finish_run` in the worker, `backend/src/worker.py:151`

**Problem**: `finish_run` now correctly propagates programming errors (e.g. `AttributeError` inside `append_event`) instead of swallowing them. In `process_one`, the caller of `finish_run` is wrapped in a broad `except Exception` handler at line 151:

```python
try:
    result = await fake_engine.repair(request, recipe, host)
    self.repo.finish_run(run_id, state=result.state, reason=result.reason)
except Exception as e:
    logger.exception("Run %s failed with exception: %s", run_id, e)
    self.repo.finish_run(run_id, state="failed", reason=error_reason)
```

When `finish_run` propagates because `append_event` raised a programming error, execution falls into the `except Exception` block, which calls `finish_run` again with `state="failed"`. But `update_run_state` in the first `finish_run` already succeeded -- the run is now `succeeded` in D1. The second `finish_run` -> `update_run_state` hits the terminal state guard (409), raises `httpx.HTTPStatusError`, which propagates out of `process_one`. `_run_loop` catches this as a transient network error, logs a warning, and continues. The run ends in the correct terminal state (`succeeded`) but without a `run.finished` event, and two spurious errors are logged.

**Why it matters**: This is not a bug in the run's final state, but the operational signature is confusing: a run that succeeded emits no `run.finished` event, and the logs show an `HTTPStatusError` 409 from `update_run_state` on a run that is in fact correctly terminated. A future on-call engineer investigating the missing event would face a misleading trail.

**Suggested fix**: Add a comment in `process_one` noting that `finish_run` can propagate for programming errors (not just engine errors), and that the outer handler's second `finish_run("failed")` call may hit the terminal state guard if the first call's `update_run_state` already succeeded. Alternatively, catch and suppress `httpx.HTTPStatusError` with status 409 in the outer handler's `finish_run` call, since a 409 in that position means the run already reached a terminal state and the error is redundant. A test covering this `process_one`-level chain would make the behavior explicit.

## Strengths

- `finish_run`'s exception narrowing is precisely right -- `httpx.RequestError`, `httpx.HTTPStatusError`, and `OSError` map cleanly to the transient infrastructure failures the docstring describes. Including `OSError` covers underlying socket-level failures that `httpx` does not always wrap.
- `test_finish_run_programming_error_propagates` directly exercises the new propagation behavior with the exact error type (`AttributeError`) that the review flagged. The test is tight and unambiguous.
- `test_run_standalone_max_runs_zero` documents the `max_runs=0` contract through a behavioral assertion: a queued run is not touched. The docstring and test together make the edge case impossible to miss.
- The D1 bridge error message change (`"Run is in a terminal state and cannot be updated"`) improves operational debuggability for both the race and non-race scenarios without touching the error code, so callers that key on `terminal_state_immutable` are unaffected.
- Type annotation modernization in `worker.py` (`D1StorageRepository | None`, `asyncio.Task[None] | None`, `int | None`) is complete and consistent within that file.
