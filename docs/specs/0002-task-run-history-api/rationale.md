# Rationale: Task, run, and history API

## Context

RepoMedic requires an HTTP application layer for Package B so that the user interface in Package A can discover repair tasks, trigger upgrade runs, inspect progress, and review run history. The system must operate fully offline during local development while adhering to team ownership boundaries: Package B owns the backend API and database storage, whereas Package A owns the Next.js frontend client.

Several forces influence this design:
First, input validation must be strict. Any invalid search mode, corrupted payload, or unknown task identifier must be rejected at the API boundary before creating database records.
Second, error responses must follow a consistent contract. Frontend clients require structured error envelopes with stable error codes rather than raw framework tracebacks or irregular error schemas.
Third, database persistence must remain decoupled. All state modifications must pass through the existing Cloudflare D1 database bridge to preserve transaction rules, atomic event sequencing, and spending constraints established in spec 0001.

## Options considered

### Option 1: FastAPI with D1StorageRepository and lifespan task synchronization

Implement standard FastAPI routes backed by Pydantic models. On application startup lifespan, scan curated task files in `fixtures/tasks/` and synchronize them into a dedicated `tasks` table in D1. Handle database operations via the existing `D1StorageRepository`.

**Pros**:
* First class Pydantic model integration with automated schema generation.
* Decouples HTTP routing from database storage mechanics.
* Retains disk fixtures as the authoring format while making tasks queryable and relational in D1.

**Cons**:
* Adds an additional database table and startup synchronization step compared to reading disk files on every request.

### Option 2: Direct SQLite file access bypassing the Worker bridge

Have the FastAPI backend directly read and write the local SQLite database file generated by Miniflare.

**Pros**:
* Eliminates HTTP hops between Python and the Cloudflare Worker bridge during development.

**Cons**:
* Bypasses Worker validation logic, atomic constraints, and token authentication.
* Tightly couples Python code to Miniflare internal filesystem paths.

### Option 3: Synchronous run execution within the POST route handler

Trigger task analysis and dependency resolution directly inside the `POST /api/runs` request before returning a response to the client.

**Pros**:
* Avoids managing background queue states for quick tasks.

**Cons**:
* Blocks client HTTP connections for long running dependency repair operations.
* Prevents progress streaming, timeout recovery, and clean cancellation handling.

## Rationale

We selected Option 1 because it maintains clean layer boundaries and robust operational guarantees. By exposing asynchronous run creation with HTTP status 202 Accepted, the API acknowledges queued requests immediately without blocking on external repair workers. 

Synchronizing task definitions into D1 on startup ensures referential integrity across the runs table while keeping local fixture files as the version controlled source of truth. Direct SQLite access was rejected because it violates the architectural boundary established in spec 0001 and fails to mirror production Cloudflare D1 behavior.
